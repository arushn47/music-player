# Manual Windows updates

For the configured GitHub Actions workflow, exact CLI/artifact verification and first-release commands, see [Windows release publishing](windows-release-publishing.md).

When a Windows update is available, an accent-colored shortcut appears immediately after **Import**; Settings → About is always available and uses the same state. Checks remain manual. Android shows a separate release/APK link with in-place installation guidance; browser builds do not show update controls. Development builds do not contact the update server. Download and signature verification finish before Restart & Update becomes available; installation exits Windows Lumaire and restarts it afterwards. The warning beside that button explains the playback interruption.

## Release setup

1. Generate an updater key pair once, outside the repository:
   ```powershell
   npx tauri signer generate -w "$env:USERPROFILE\.lumaire-updater.key"
   ```
   Back up the private key and password securely. This key is separate from Android APK signing and Windows Authenticode signing. Never commit it.
2. The matching **public key** is now configured in `plugins.updater.pubkey` in `src-tauri/tauri.conf.json`. Keep the existing key pair; do not regenerate it. The endpoint is `https://github.com/arushn47/music-player/releases/latest/download/latest.json` and must be publicly accessible without an account.
3. For release builds, set `bundle.createUpdaterArtifacts` to `true` using a release config overlay. Keep it out of routine unsigned local builds. For example, save this as a local release config:
   ```json
   { "bundle": { "createUpdaterArtifacts": true } }
   ```
4. Supply these GitHub Actions secrets as environment variables on the Windows build step:
   ```yaml
   env:
     TAURI_SIGNING_PRIVATE_KEY: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY }}
     TAURI_SIGNING_PRIVATE_KEY_PASSWORD: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY_PASSWORD }}
   ```
   `TAURI_SIGNING_PRIVATE_KEY` contains the private key contents. Build with `npm run tauri -- build --bundles nsis --config path/to/release-config.json`. Increment the application version for an actual new release. A release publishing workflow also needs `contents: write` and `GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}`; that token stays in CI, never in the app.
5. Upload the signed installer and its generated `.sig` plus `latest.json` to the same published GitHub Release. The manifest uses the complete signature file contents, the actual installer URL and an RFC 3339 date:
   ```json
   {
     "version": "1.0.5",
     "notes": "Describe the changes here.",
     "pub_date": "2026-10-20T00:00:00Z",
     "platforms": {
       "windows-x86_64": {
         "signature": "CONTENTS_OF_GENERATED_SIG_FILE",
         "url": "https://github.com/arushn47/music-player/releases/download/v1.0.5/Lumaire_1.0.5_x64-setup.exe"
       }
     }
   }
   ```
   These are illustrative version/asset names; use the actual generated files. `tauri-apps/tauri-action` can generate and publish the manifest with `includeUpdaterJson: true` instead of assembling it manually.

## Verification and limits

Run `npm run build`, `npm test` and a native Windows build. Before shipping, test a real upgrade between two signed versions: manual check, release notes, progress, continued playback during download, explicit restart, signature rejection, and retained library/settings. Also check offline retry and a missing manifest (404); neither may claim the app is current.

The existing 1.0.4 release files predate this implementation and must be replaced through a manual installer before those users can receive in-app updates. No release was published and no signing key was generated by this implementation.

Official references: https://v2.tauri.app/plugin/updater/ and https://v2.tauri.app/reference/javascript/updater/.

## Release notes before and after an update

- Finalize `RELEASE_NOTES.md` only when the release is ready. Its first line must be `# Lumaire vMAJOR.MINOR.PATCH` matching the tag. The v1.0.5 release notes are finalized; the publishing workflow rejects a heading that does not match its version tag.
- The Windows workflow uses this file as the release body and updater manifest notes. Manifest validation rejects missing/empty notes. Version 1.0.5 retains the existing signing identity.
- Users see the target version's notes before downloading. A verified download does not install until **Restart & Update** is clicked. The target notes are saved locally before installation; they appear as **What's new** only after that exact version starts. Failed/cancelled installation does not claim success.
- Bundled notes also cover manual upgrades and Android APK upgrades; first installed launch shows them once. The current installed notes remain readable from Updates/About after dismissal. Startup reads version/local notes only; it never checks a server automatically.
- Android currently opens GitHub release notes and APK downloads in the browser. Opening the newer APK invokes Android's installation confirmation. Same application ID, compatible certificate and a higher version code are required to update without uninstalling or deleting app data. Keep the release keystore stable. This is not an embedded Android downloader or silent installer.
- The 1.0.4 preview cannot bootstrap through the updater: run the 1.0.5 Windows installer manually once. A future signed version is required to exercise the full installed-app updater path. Android APK certificate continuity is checked during release preparation; physical-device replacement testing is separate.
